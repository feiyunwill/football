## 入口

具备原生依赖的 Linux 环境中，Host 与 Join 必须显式选择相同传输：

```text
python -m gfootball.frame_sync.main_menu --mode host --transport udp
python -m gfootball.frame_sync.main_menu --mode join --transport udp
```

省略 `--transport` 使用 TCP。传输选项只作用于本次菜单的 Host/Join，不修改持久化设置文件。菜单显示实际传输和监听端口；输入、设置、保存及回放路径与[多人比赛入口](multiplayer_match.md)一致。每个受控槽位仍需要一个已 Ready 的玩家。

嵌入 API 使用 `HostedMatch(..., transport='udp')` 和 `NetworkPlayer(..., transport='udp')`，生命周期保持 `start/advance` 或 `tick/finish/close`。也可直接使用 `MatchUDPServer`、`MatchUDPClient` 和 `MatchReconnectingUDPClient`。`udp_limits` 传入现有 `UDPLimits`，Host 另可接收 `cookie_limits`；在 TCP 模式传入 UDP 限制会明确报错。

TCP 和 UDP 客户端共用 MatchClientProtocol 的原点、控制缓冲、显式版本握手与结束消息；UDP 继续使用已有单 IO 所有者和恢复线程。原点校验、身份检查和 `set_state` 顺序保持有效。通过 cookie 返回路径检查后才分配 Peer，每次连接/恢复使用新的传输 epoch，旧连接数据不会进入新字节流；比赛控制 epoch 独立管理输入与暂停代次，两者不能混用。

数据报最多 1200 字节，其中可承载应用数据最多 1184 字节。比赛原始快照最多 1 MiB，加最多 4096 字节元数据与 12 字节内部头，仍增量分片和接收。客户端最小可配置字节流缓冲为 512 字节；收到较大数据报时分段交给同一解析器，整份数据报被接受后才确认，不增加无界分片列表。

UDPState 继续按发送/接收包数、保留字节、交付期限和重试次数限制工作量。完整 1 MiB 原点不代表预测历史也能持有同样大小的 Python 对象；历史预算计入对象开销，容量不足时现有逻辑停止预测并等待权威帧。测试中的大快照归约器具有独立的短规范摘要，并实际验证了这一路径；没有扩大生产预算来通过测试。

## 恢复与退出

断开客户端会关闭旧 IO worker/socket，后台恢复所有者以新 epoch 和原 token 重试；恢复完成后在玩家线程恢复原引擎、检查原设置/资源身份，再进行 Ready/handback。服务端原地址尚未超时期间会拒绝恢复请求，等待下一次尝试。恢复总期限应容纳单次握手和服务端断线检测：局部检查使用单次 0.3 秒、总计 3 秒和服务端空闲 0.4 秒；生产默认分别为 5 秒、60 秒和 3 秒。总期限短于单次握手时，第一次被拒绝的 UDP 尝试可能耗尽恢复时间，不承诺在这种配置下恢复。

v6 不自动降级到旧比赛版本，也不在失败后新建比赛。损坏原点、不匹配节拍或非法控制元数据在工厂前拒绝，资源身份不符在 `set_state` 前拒绝。MatchReady 确认节拍及控制 epoch，重连时原点过期会拒绝确认并重试同一会话。不同比赛版本的连接失败。

收到比赛结束后，玩家处理完权威帧、撤销超过终点的预测、核对最终校验值并排入 EndAck。EndAck 入队后停止产生新心跳，现有 IO worker 继续处理可靠传输确认。`output_pending()` 同时计入应用发送队列和 UDP 中尚未确认的包；`flush_end_ack()` 默认最多等 2 秒，持续丢失明确报超时。

服务端区分 `finish_acknowledged()`（收齐应用结束确认）和 `finish_settled()`（完成传输退出等待）。UDP 收齐确认后继续保留接收端约 1 秒，用于应答重传的 EndAck；外层结束期限仍有优先权。该期限不是无限丢包保证。Host 返回的 `end_acknowledged` 表示是否收齐应用确认；不同线程之间确认到达的竞态已处理。TCP 收齐确认即可结束。
