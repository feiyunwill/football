# Python 帧同步服务端

2026-09-10：同步与异步服务端共用 `ServerRuntime`。网络解析、输入窗口、发送队列和会话恢复由同一实现维护；同步 API 将调用提交给一个自有事件循环线程，异步 API 在调用方事件循环中执行。场景构造、step、快照和关闭也由该所有者调用。

## 启动与关闭

原有 `gfootball.frame_sync.server.FrameSyncServer` 与 `server_async.FrameSyncServerAsync` 导入路径保留。构造参数新增关键字 `limits=ServerLimits(...)`、`engine_factory` 和 `handshake`。默认工厂创建真实 GameEnv；可注入符合引擎接口的独立适配器，测试使用明确的确定性输入归约器，不代表真实引擎验收。

同步入口 `start()` 完成监听后返回；`stop()` 等待所有者退出。跨线程待处理 API 调用最多 8 个，满时明确报 `control_capacity`。关闭请求单独合并，不与普通查询争用该容量。原生引擎调用不能被 Python 强制中断；启动/停止的 30 秒等待截止不保证原生线程已经退出，失败后不能在原对象上重新启动。

异步入口用 `await start_server()`；兼容的 `start()` 只初始化引擎；后续监听和关闭必须留在初始化线程，跨线程迁移会在修改所有权前被拒绝。`stop()` 立即禁止新帧并调度关闭，`await close_async()` 等待完整清理。取消某个关闭等待者不会取消共享清理任务。推荐 `async with FrameSyncServerAsync(...) as server`。实际客户端对应 `await client.close_async()`，避免只请求关闭后马上终止事件循环。

监听端口 `0` 可由操作系统分配，启动后读取 `listen_port`。同步服务端默认 `handshake='negotiated'`，异步服务端默认 `'server_first'`，分别保留现有同步与异步客户端的握手方式。跨组合使用时显式选择匹配模式。

`run_one_frame()` 和 `run_loop()`/`run_loop_async()` 只允许一个帧调度者。`get_env()` 是兼容的借用访问，应仅在引擎空闲时使用；客户端预测必须创建自己的引擎。可运行的权威帧消费示例见 [现代化入口](MODERNIZATION_PHASE3.md#32-帧同步-asyncio-与同步入口)。

## 容量与超时

| 对象 | 默认边界 |
| --- | --- |
| 连接 | 32 个，正在取消 I/O 的连接仍计数；每个连接一个接收任务、一个发送任务 |
| 控制槽 | 左右各最多 11，共最多 22；每个连接一个槽 |
| 输入 | 当前帧与其后共 128 帧；拥有的输入值合计 256 KiB |
| 接收 | 每连接 8 KiB，包括实际 bytearray 容量；每轮最多处理 64 条再让出执行 |
| 发送 | 每连接 256 条、2 MiB；包含活动写入、重连等待 Ready 的历史 |
| 快照 | 1 MiB；超限拒绝恢复 |
| 入站速率 | 每连接 1,000 条完整消息/秒，突发 128 条 |
| 超时 | 握手 5 秒、Ready 30 秒、完整消息 2 秒、空闲 3 秒、发送 5 秒 |
| 心跳 | 默认 1 秒，Python 客户端也周期发送，等待大厅无需提交游戏输入 |

限制接受有限范围的严格类型参数，不接受负数、无穷数或布尔值充当整数。发送截止从最初入队开始计算，排队和等待 Ready 不重置截止。关闭时先取消实际 I/O，待取消完成才关闭套接字句柄，并释放活动发送占用。

输入消息先验证完整结构、帧窗口、有限方向值、按钮位和已分配槽，再原子地入队。完全重复幂等，冲突重复关闭违规连接；输入满、非法或超出未来窗口不会覆盖已有输入。收集开始不清空提前收到的当前帧和未来帧。断线时保留已经接受的当前输入，删除断线者的未来输入；缺少的 bot 槽才由接管器填充。

`stats()` 返回连接、会话、输入、发送、接收占用及固定失败原因。字节数计量自有保留数据，字典、任务等控制结构另由数量限制；不代表进程 RSS、操作系统 socket 缓冲、临时编码、副本、原生或 GPU 的硬上界。

## 断线恢复

会话使用随机且非零的 64 位令牌。显式协商 v3 的客户端会在元数据后收到 SessionToken；普通 v2 保持兼容，宿主仍可调用 `get_session_tokens()`（异步版本需 await）取得实际令牌。令牌不能由种子或槽号推算。当前链路本身不提供 TLS。

比赛开始后，新连接必须用属于已断线会话的 `ReconnectRequest`。服务端发送 SessionStart、槽分配、下一权威帧编号对应的状态快照和接管通知。客户端恢复独立引擎后才发送 Ready；期间 bot 继续推进，后续权威帧在同一发送预算内保持顺序，Ready 后释放并发送 Handback。令牌错误、会话仍在线、快照过大或恢复期间积压超限均明确拒绝，不会抢占其他 bot。
