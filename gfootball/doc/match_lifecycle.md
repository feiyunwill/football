# 比赛自然结束、预测与持久化

2026-09-10。默认 `native_match_engine()` 在同一个引擎名额内使用 `MatchLifecycleEngine`，为本地比赛、Host/Join 和独立回放执行可保存、可回滚的终局规则。公开 GameEnv 绑定、Core 和旧版通用 `native_engine()` 没有改用该规则；嵌入方自定义引擎可通过返回严格 bool 的 `is_match_finished()` 明确提供结束能力。

## 终局规则

规则读取实际 ScenarioConfig，比赛过程中不得改变。每次 `step_with_input()` 后读取实际观察，按以下优先级记录结束原因：

| 原因 | 条件 |
| --- | --- |
| `duration` | 引擎的 `info.step` 达到 `game_duration` |
| `score` | 启用进球结束，且任一方已有进球 |
| `out_of_play` | 启用出界结束，且模式从正常比赛转为非正常比赛 |
| `possession_change` | 启用球权切换结束，且最后一个已知持球队发生改变 |
| `engine` | 引擎自身已经结束，或调用适配器的 `finish()` |

时长使用引擎有效比赛计数，暂停比赛的时间不靠网络帧号累加。原生 reset 的开球前 `step=-1` 有效；首帧之前的模式和持球队均记为未知。无人持球时保留此前已知球队，因此争抢后的球队变化仍能触发规则。

终局规则成立时调用原生 `finish()`，最终一帧仍进入摘要、录制和比分结果；之后的 `step_with_input()` 明确拒绝。`get_match_end_reason()` 返回原因，未结束时为 None。此适配器是一次比赛的帧输入接口；`step()` 和 `reset()` 明确拒绝，回滚使用 `set_state()`，新比赛创建新实例。公开原生绑定接口不受这些限制。

## 权威结果与预测

客户端预测到终局后暂停新的输入采样和预测，继续重试已有输入并接收权威帧。预测结果可以被纠正：假进球可回滚后继续比赛，权威输入导致更早终局时会清理后续预测及其缓存。停止或失败的逻辑查询不再访问引擎。

权威端在最终帧及状态校验消息之后发送现有 MatchEnd。客户端收到并核对权威终点后才确认结束，TCP/UDP 继续使用现有 EndAck 和 UDP 传输退出等待。终局预测本身不会关闭比赛，也不会发送结束确认。

`HostedMatch.run()` 在权威端结束后进入正常收尾、保存和录制发布。`advance()` 不再推进已经结束的权威比赛。公开 TCP/UDP 服务端循环也自动收尾。本地 `run()` 在终局帧之后发布产物、释放资源；载入已完成存档可以检查状态，继续运行会以零个新帧结束。终局回调或输入失败时保留旧录制文件，次要清理错误不会覆盖主异常。

## 快照兼容性和预算

比赛快照使用 `FMTERM1\0`，包含 29 字节固定头、32 字节 SHA-256 和原生快照。头记录规则、前一模式、最后持球队、终局原因和原生长度。整份仍最多 1 MiB，原生负载最多 1,048,515 字节；不会为头部增加扩大原预算。

恢复先验证大小、格式、规则和完整校验，再调用原生恢复；恢复后核对配置、观察历史和终局状态。失败恢复旧原生状态及原有策略；连恢复备份也失败时关闭资源。恢复过程中会临时保留原生备份，这不是每次原生分配或整个进程 RSS 的上限。
