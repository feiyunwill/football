# 真实比赛性能测量契约

对应 ms-21.1 → plan-21.1.1 → task-21.1.1.1。基准提供可复现的优化前证据；性能预算、优化收益和长时间内存稳定性由后续任务分别验收。

## 场景与时间单位

- 使用正式 football_engine、默认 11v11 场景、种子 42/43、每队两个外部控制槽位，其余球员执行正式 AI。
- 四个槽位共享确定性输入生成规则：八方向移动、周期性冲刺、短传和射门。完整输入序列在测量前生成，记录其字节哈希。
- 每个独立进程先运行 200 个预热逻辑帧，再测量 2000 帧。每种种子启动五个独立进程，交替种子顺序；合计 20000 个稳态帧。
- 一个 StepWithInput 逻辑帧推进十个 10 ms 物理 tick，即 100 ms 模拟时间。报告中的耗时是整个逻辑帧耗时，不能直接当作单个物理 tick 的 p99。
- 至少四分之一的样本必须处于比赛进行中；逐帧记录 IsInPlay()，同时给出进行中和停球阶段的分布。还检查真实球员数量、时间推进和存在主动踢球记录。kicked_history_frames 是观察到踢球历史的帧数，不是独立踢球次数，也不代表 AI 质量验收。

## 测量边界

- Release、C++23、-O3 -DNDEBUG，不允许 sanitizer、-Ofast 或 -ffast-math；保存实际编译命令和编译器版本。引擎及测量程序保存 SHA-256。
- 子进程固定到可用 CPU（默认最小 CPU 编号），保存处理器型号、亲和性、拓扑、内核、内存、cgroup 和可读取的 governor。WSL 主机负载、温度和动态频率没有被锁定；这些数据只代表记录的开发机器。
- 启动时间只计 start_game()，在每个全新进程测量，并与预热、稳态、关闭分别记录。文件系统缓存不清空，因此不能宣称磁盘冷启动。进程总耗时另存，包含测量、重演及销毁。
- 稳态 wall time 只覆盖正式 StepWithInput()；使用单调 steady_clock，单位 ns。另存每帧进程 CPU 时间，辅助判断调度噪声。
- 输入生成、容器预留、快照存储不进入稳态计时。每 100 帧采集状态哈希和 RSS，位于计时区间之外；单独记录诊断耗时及整个循环耗时。采样仍可能影响后续缓存行为，因此优化前后必须使用同一采样契约。
- RSS 使用 /proc/self/smaps_rollup 的 Rss，kB 乘 1024 转 bytes；启动、预热、稳态检查点、关闭均记录。getrusage 的峰值另存，其统计包含重演，不能与稳态采样最大值混为一谈。Linux 的 statm resident 使用近似计数，精确采样应使用 smaps/rollup，见 [Linux proc_pid_statm 文档](https://man7.org/linux/man-pages/man5/proc_pid_statm.5.html)。
- 保存全部原始 ns 样本；分位数使用 nearest rank（排序后第 ceil(n*p) 个值）。汇总给出每种种子的合并分布及各独立进程 p99，不能只挑最快一次。

## 正确性与证据

每个进程保存预热快照，测量后恢复并重演全部 2000 个输入，要求最终规范状态哈希相同。五次独立进程还必须具有相同输入、预热状态、最终状态、途中状态检查点和比赛进行标记。计时摘要由 Python 根据原始样本重新计算，拒绝篡改的分位数、缺失样本、静止轨迹、缺少进程及重演失败；这些拒绝路径有独立负向测试。

执行：python3 .project/checks/match_benchmark.py。正式验收：python3 .project/quality.py run task-21.1.1.1。原始证据写入 .project/optimization/benchmarks/match-<timestamp>.json，末行 JSON 输出其路径、SHA-256、源码指纹和摘要，正式运行器将其保存在验收日志中。源码身份范围由门禁 manifest 定义，测量前后均核对源码及二进制未变化。

后续优化保留此基线文件。比较必须确认场景、输入和构建契约一致，在同一机器交错运行优化前后版本，并验证轨迹未变。该无渲染基准不能证明显示帧率、输入延迟、网络质量、GPU 性能或整体产品质量；这些由对应里程碑的真实路径验收。
