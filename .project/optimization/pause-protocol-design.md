2026-09-10，ms22 → plan22.1.2 → task22.1.2.1。Python TCP/UDP v6、Local 同步权威暂停、图形/终端请求和状态反馈已接入并有真实 socket/文件检查。Local 通过专属同步推进边界实现，不向通用连接发送 v6 控制。引擎/显示为 oracle；真实原生、设备、画面与性能尚未验收。

1. 暂停由本地权威所有者请求。已经开始收集的权威帧完成后再建立边界；暂停期间不执行物理步进，心跳、传输和恢复继续工作。
2. v6 控制状态包含 epoch、phase、next_frame、规范状态 hash。RUNNING → PAUSED 和 PAUSED → RESUMING 分别递增 epoch；所有在线参与者确认恢复准备后，广播同 epoch 的 RUNNING 提交。禁止跳过准备直接恢复。
3. 客户端先停止产生新预测，按原预算排空边界之前的权威帧；撤销越过边界的预测并核对 hash。随后清空本 epoch 作废的未确认输入、重试状态及输入边沿，再确认控制消息。既有权威记录不改写。
4. 新输入携带 epoch。服务端清空边界之后的输入窗口；旧 epoch 在恢复后也不能重新生效。帧号可在新 epoch 中重新采样，同一 epoch 内原有不可变输入约束继续生效。
5. 逻辑、输入和显示所有者各自处理控制状态；IO 线程不访问引擎。RESUMING 仍冻结输入和预测；只有 RUNNING 提交解除冻结。恢复不累计墙钟时间债务。
6. 初始及重连原点元数据携带 epoch/phase，v6 MatchReady 确认它。恢复过程中代次变化要拒绝过期确认并重试原会话；断开的玩家沿用已有 AI 接管政策，回归玩家在新原点验证后才交还控制。
7. 每个连接只保留一个待确认控制状态，主机只保留一个最新暂停意图。确认有明确期限，超时移除该连接，不能被仍发心跳但不确认的客户端永久阻塞。控制消息与权威消息共用可靠有序字节流；UDP 的 cookie/epoch 传输继续独立生效。
8. 保存的物理比赛状态与临时会话控制分开。暂停不改变物理摘要，不因保存、回放或新会话而重放旧输入。结束和退出必须在暂停中仍能正常收尾。

TCP/UDP v6 启用编号 19（18 字节控制）、20（17 字节确认）、21（11 字节头加每槽 12 字节输入）。Local/Host/Join 已接入所有者和图形输入冻结，K/Guide 可由 Local/Host 请求暂停；Join 仅接收权威控制。原生 HUD 源码已实现，真实原生与产品验收完成前四个 ready 标志保持 false。

必需自动证据包括：TCP/UDP 的暂停屏障与恢复提交、越界预测回退、暂停前晚到输入/重试拒绝、确认超时、暂停期间断线恢复、保存/结束/退出、持续按住与短按、真实设备和 GameEnv 摘要、中间图像、长暂停无大步长，以及既有比赛/网络/录制回归。

客户端控制读取必须提供“首条尚未应用的控制”，不能覆盖为最新值。否则同一收包批次内的 RUNNING 提交和下一次 PAUSED 会让逻辑层跳过合法的中间状态。客户端可保留至多两条小型控制记录（一条待消费的提交、一条待确认的屏障）；服务器在屏障 ACK 前不得再生成后续代次。`acknowledge_control` 在可靠队列接纳 ACK 后消费暂停/恢复准备，`commit_control` 仅在逻辑层应用 RUNNING 后消费本地记录，无额外线上确认。权威帧与提交同批到达时，先应用提交再执行该帧。
