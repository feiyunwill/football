# 比赛帧回放：容量、所有权与文件实现

归属：**ms-21.1 → plan-21.1.2 → task-21.1.2.1**。

本轮实现独立 `frame_sync/replay.py` 的有界录制、完整序列化、持久化和可寻址读回，**64/64 Windows 检查通过**。这是实际 Python 数据与文件验证，没有执行 GameEnv 或渲染比赛。整体 `memory_budget.ready=false`，当前任务和总体优化目标继续保持未完成。

## 发现与实现

原 `Replay` 可以无限追加帧和事件，`ReplayManager` 只限制保存场数；返回的对象和内部嵌套字典可继续修改，绕过任何集合容量统计。重复 ID 还会先淘汰一场历史再覆盖同名记录。`ReplayFrame.to_dict()` 丢失球员位置及输入，事件序列化遗漏 details，模块没有实际文件读写与读回游标。

新增 `replay_data.py`、`replay_store.py`、`replay_file.py`；原导入路径成为兼容入口，旧实现按仓库规则保留在注释中。帧/事件保留构造参数、可读字段、值相等比较和完整 `to_dict()`；外部原始容器及导出副本均不与存储共享可写数据。

首次不可变实现采用 frozen dataclass，检查实际复现了 `__dict__` 可修改字段的缺口；随后改成 Python 3.9 可用的显式 slots 和写保护，仍支持弱引用。不能用 `dataclasses.asdict()` 处理新值对象，使用完整 `to_dict()`。项目声明 Python >=3.9，新增四份生产源码完成 3.9 语法解析，实际 3.9 运行并未执行。

单场有帧、事件、记录字节、总字节限制。索引预先按容量定长，记录按 64 个位置分块分配，使用实际列表块与数据对象尺寸计量，不猜测动态列表扩容。数据图限制深度、节点、容器、字符串、玩家数量和整数/浮点范围，拒绝循环及用户自定义转换对象。

管理器对活动和已保存回放采用同一个锁与预算，调用方直接使用活动 Replay 也会计量。增长时可淘汰最早创建的已封存历史；先验证新工作与所有淘汰候选能够满足限制，再修改集合。重复 ID、非法数据或无法容纳的活动切换不会提前封存当前录制或删除历史。停止、淘汰、删除、关闭后的外部引用均封存。

导入最多一项同时进行，单独限制一份单场暂存容量，完整验证后才提交到集合。关闭会发出取消请求，读入线程在下一次读取前退出并关闭文件；正在阻塞的系统调用不被强制中断。集合字节统计与导入暂存上界分开报告，直到清理结束 `loading` 才回到 False。

文件采用版本 1 JSONL，逐条保存全部帧、球员位置、输入及事件详情。头部给出元信息与记录数，尾部给出计数和全部前置原始行的 SHA256。读取端同时检查文件大小/身份/变化、单行长度、字段结构、帧连续性、事件顺序、时长、正常尾部与校验和。JSON 重复键、非有限数及超长整数在转换时拒绝。

写入复用现有跨进程目录预算和 AtomicReplayFile，完整写入、fsync/关闭后才替换明确目标。取消、编码、容量和发布失败不替换已有目标。ReplayFileReader 只保留元信息、计数和校验状态，一次返回一条不可变记录；提前关闭不表示完整验证。Replay.load 只返回完整验证后的封存数据，游标可 seek/rewind，多个调用者共享游标时也不会重复推进同一帧。

## 默认边界

| 数据 | 限制 |
| --- | --- |
| 单场 | 100,000 帧、10,000 事件、128 MiB |
| 单条 | 64 KiB、位置/输入各最多 22 玩家 |
| 集合 | 活动加历史 50 场、256 MiB |
| 暂存导入 | 同时一场，额外最多一份单场预算 |
| 文件 | 128 MiB，每行 512 KiB |
| 数据图 | 2,048 节点、8 层、容器 128 项、字符串 4 KiB |

字节统计包括记录数据及索引/块的持有容量；控制对象由场数等限制。调用方保留已淘汰数据、显式导出副本、临时编解码、64 KiB 文件读缓冲、解释器/原生/RSS/GPU 不属于集合字节统计。每个 Replay 自身仍保持单场上界。容量限制同时生效，不保证 10 万条最大尺寸记录可放入默认 128 MiB。
