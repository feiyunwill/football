## 实现与审查结论

旧 `LogicStateHolder` 只限制 deque 条数，单个状态和累计字节均无上界；构造参数可使缓存无限增长或无法保留有效历史。回滚后失效的历史也没有清理规则。旧 `PresentationLoop` 分别调用 `read_interpolated()` 和 `read()`，两次读取之间可能发生发布；每次绘制都重新执行 `set_state()`，并额外保留两份状态引用。

新增 `presentation_state.py` 与 `presentation_loop.py`，原 `presentation.py` 保留原类的日期/原因注释并导入新实现，原来的公开导入路径保持可用。

`LogicStateHolder` 现在发布不可变的 `PresentationState`。一次原子读取包含状态、当前/确认帧、单调时间、等待标记、发布版本、状态内容版本和不连续标记。公开记录类型本身也验证 payload 不可变性、字节上限、帧关系、时间、标记及版本范围；仅使用 frozen dataclass 并不能保证内部 payload 不可变。

写入前验证单状态容量、帧关系和标志，随后在锁内暂存一组有界引用再提交。过大的状态明确拒绝并保留上一份有效发布；展示历史达到数量或累计字节上限时淘汰最旧的展示记录。回退帧、同帧内容修正或显式不连续发布会清除旧历史。确认帧不能倒退，也不能超过显示帧；新的逻辑会话通过 `clear()` 开始。

元数据更新复用相同的不可变状态内容，不重复追加同一帧记录，也不重置该内容的发布时间；另行记录最近写入时间，避免这种更新掩盖时钟倒退。`clear()` 和 `close()` 都释放缓存，版本号不复用，关闭后拒绝新发布。返回给外部读者的旧样本仍然自洽。

`ClientLogicLoop` 在发布时传递 `discontinuity`：即使修正和重演后显示帧编号继续增加，也会使展示层清除已经失效的历史。自定义状态接收器的 `write()` 需要接受这个关键字；仓库实际 holder 和本轮逻辑/展示合同已接入。

`PresentationLoop` 每帧只读取一个原子样本，环境调用发生在 holder 锁外。仅当状态内容版本改变时调用 `set_state()`，仍然按显示节奏调用 `render()`；等待/确认元数据变化不会触发重复恢复。同帧内容修正会恢复新状态，清空 holder 时停止绘制旧画面。消费端只保存版本号和有界时序样本，不再保存额外的序列化状态历史。

恢复或绘制抛错后停止后续环境调用，只保存一个固定失败原因，不保留异常及其 traceback。停止可唤醒低帧率等待；帧调用和循环生命周期分别防止并发与重入。传入的显示环境由调用方拥有，必须与逻辑环境分离，并在合适的渲染线程创建/关闭；本轮没有新增原生窗口所有权管理入口。

`read_interpolated()` 保留兼容接口，返回最新完整状态及自最新发布开始计算的诊断相位。它没有对不透明状态实施坐标/姿态插值。本轮没有把这个相位当成实际视觉平滑的证据。

## 容量与工作范围

| 项目 | 默认 | 硬上限或拒绝行为 |
| --- | --- | --- |
| 展示记录数量 | 4 | 1–64，超出淘汰最旧记录 |
| 单个不可变序列化状态 | 1 MiB | 1 MiB，按 `sys.getsizeof(bytes/str)` 检查 |
| 展示历史状态字节 | 4 MiB | 可配置至 8 MiB，单状态放不下则拒绝 |
| 发布/内容版本 | 单调递增 | 64 位范围，耗尽拒绝新发布 |
| 渲染时序样本 | 100 | 1–1,024，最近样本环形存储 |
| 渲染频率配置 | 60 Hz | 有限数值，1–240 Hz |

历史字节按每条记录引用的状态对象收费，共享同一 payload 的不同帧会被保守地重复计入。容器/记录元数据另受数量限制；外部读者保留的样本、调用方已分配的状态、原生反序列化暂存、引擎对象、GPU 和进程 RSS 不包含在这个数字内。

时序统计是渲染调用开始时间间距的误差，p95 使用 nearest-rank。它不是屏幕呈现延迟或目标 GPU 性能验收。执行环境回调也不受硬实时截止时间控制。
