# Python UDP 自动恢复实现与局部验收

本轮属于 `ms-21.1 → plan-21.1.2 → task-21.1.2.1` 的资源预算与恢复生命周期实现，并为网络里程碑准备可复用传输。目标仍为 ACTIVE；本任务、整体内存预算与 ms-21 至 ms-26 尚未完成。

实现了真实 cookie/epoch UDP 服务与客户端，复用已有服务端会话/输入/快照流程和客户端恢复状态机。旧 UDP 重连包装器已保留为注释并替换；它此前在 tick 中阻塞连接且创建新会话，无法恢复原比赛。使用新包装器必须配套新 Python UDP 服务，原有初始会话客户端保持旧协议。

具体包括：29 字节无状态地址验证、逐次连接标识隔离、有界过期记录防止 CONFIRM 重放、一个 UDP socket 与事件循环所有者、按需快照分片、按序交付后 ACK、快照应用后 Ready、收到 Handback 后继续逻辑、单一后台重连所有者和关闭回收。详见 [协议与 API](../../gfootball/doc/frame_sync_udp_resume.md)。

审查和测试实际发现并修复了两类问题：

1. 先确认乱序片段会释放发送压力，使大快照在等待丢失片段时撑满接收队列。新协议改为按序交付后确认，未来片段保持未确认，接收与发送容量形成背压。对应真实故障代理和独立状态测试已通过。
2. TCP 的超时类型通过等待返回后再次采样时钟判断，在 Windows 时间边界出现 `handshake_timeout` / `recovery_timeout` 误判。现在保留实际限制等待的期限类型，UDP 同步采用此规则。失败归档 a 保留，修复后完整重跑归档 b。

首次 UDP 大快照试跑失败时还暴露了测试清理提前抛错后未停止服务端的问题；测试清理改为完成全部资源回收再报告错误，故障代理容忍清理阶段 ICMP。该失败进程已结束，最终归档无遗留所有者。
