# 本地比赛录制、保存与继续的局部实现

本轮继续 `ms-21.1 → plan-21.1.2 → task-21.1.2.1` 的实际入口和资源所有权接入。优化目标保持 ACTIVE，整体 memory_budget 尚未就绪，后续手感、网络、渲染、AI 与发布里程碑仍未完成。

原来的 LocalPlayer 没有客户端引擎，收到权威帧后还把 SlotInput 列表错误地解包为槽位条目；启动依赖空闲端口预探测和固定 sleep，菜单没有保存继续与录制回放入口。现在 LocalPlayer 使用真实 TCP 权威端与实际引擎接口的副本，逐帧输入、确认、推进并比较规范状态摘要，加入单线程所有权、重入保护及完整退出清理。

新增 `match_archive.py` 和 `local_runtime.py`，旧 `local_play.py` 实现保留为注释并导出新入口。`main_menu.py` 的本地比赛已调用新运行器，并增加保存继续与回放选项。`replay_data.py` / `replay_file.py` 增加显式 v2 原生快照事件，普通回放保留 v1。详细 API、命令和限额见 [使用说明](../../gfootball/doc/local_match_storage.md)。

存档使用原有有界单槽位集合与完整原子提交，首次创建不写空记录。每份原生状态最多 1 MiB，最多 43 个编码块，槽位预算 2 MiB；读取前校验结构与尺寸，解码后验证 SHA256。录制使用现有 ReplayManager 预算，保存真实初始状态、位置、输入和最终规范摘要；续玩录制具有自己的完整原点，能独立重放。

## 当前执行证据

`python-local-match-windows-20260910-b`：120 项全部通过，其中比赛集成 21 项、既有帧回放和辅助功能 64 项、存档 35 项。无 skip、失败、错误、ResourceWarning、异步任务警告、残留自有线程、跟踪子进程或目录锁描述符。实际平台为 Windows Python 3.14.6；8 个生产入口的 Python 3.9 语法检查通过，但未执行 3.9 运行时。

测试覆盖：

- 真实 TCP 比赛 3 帧保存后继续至 6 帧，从保存点再继续 3 帧，最终状态一致；原比赛和续玩录制分别完整重放并匹配。
- 1 MiB 原生接口快照实际保存、读取、43 块编码和 v2 回放文件；零帧续玩保留已存在的比分。
- 失败的原子替换、录制容量超限、副本工厂/恢复/推进和回调异常，全部回收已拥有资源，既有输出文件不被部分结果替换。
- 每帧输入校验、跨线程和重入拒绝，完整文件校验通过但位置内容错误的回放仍被实际执行校验拒绝。
- 菜单本地比赛、保存继续、回放调用同一个实际运行器；测试仅通过显式工厂提供独立 Adler32 归约器，没有替换原生模块或提取类体执行。
- 新进程读取实际存档时不加载 GameEnv，CLI `--help` 正常展示保存/录制/继续/回放选项。

当前界面仍为终端文字输出，没有实现图形回放、SDL 按键事件或完整 Host/Join/Settings 流程。之前的 Host 只等待连接、Join 不推进比赛等旧代码仍需接入新的比赛客户端；这些问题不会因本地路径通过而被标记完成。存档也缺少跨引擎二进制/资源身份保护、迁移和云同步。
