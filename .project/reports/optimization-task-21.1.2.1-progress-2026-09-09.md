# 网络与回滚内存预算：实施进度

归属：ms-21.1 性能与容量 → plan-21.1.2 容量与预算 → task-21.1.2.1 网络与回滚内存预算。

本任务仍在实施，`memory_budget.ready` 保持 `false`。本文记录已实现并局部验证的快照、回放和 UDP 边界，不代表整个任务或网络里程碑验收通过。

## 已实现的边界

| 模块 | 默认边界 | 到达边界或失败时的行为 |
|---|---|---|
| FrameSimulation | 1–22 个受控槽位；权威帧窗口 1024；输入容量 512 KiB；单快照 1 MiB、历史 8 MiB；预测帧数仍至多 8 | 在推进前暂停超预算预测；继续确认权威帧。纠正重演时快照增长超限，恢复到已纠正的权威帧并清理后续预测 |
| ClientState | 历史数量参数 1–1024；单快照 1 MiB、总历史 8 MiB | 重复帧替换；按数量和保留字节淘汰；拒绝非法参数/输入；失败保存保留已有快照；移动后的对象仍可使用 |
| ReplayRecorder / ReplayPlayer | 100000 帧、32 MiB；槽位 1–22；场景文本最多 1024 字节 | 录制满载后保留可序列化的有效前缀和停止原因；加载先校验完整载荷，再一次提交，失败保留原播放状态 |
| ReliableUDPChannel | 单报文 1200 字节（含 7 字节传输头）；未确认包 256 个、有效载荷容量 256 KiB | 校验后再分配与消耗序号；ACK 释放容量；满载拒绝可在 ACK 后恢复；套接字失败或重传耗尽关闭通道并释放待发送数据 |
| UDP 会话接收 | 每会话接收容量 4096 字节；客户端权威帧/哈希各最多 1024 项 | 追加前校验保留容量；槽位声明和输入不合法、队列满或窗口拒绝时停止连接，客户端返回非零退出码 |
| UDP 服务器会话 | 每队至多 11 个受控槽位，总数 1–22；每个保留会话必须占有至少一个槽位 | 构造时在输入分配前校验；失败会话释放报文与接收缓冲。当前比赛中的槽位仍保留，完整重连策略属于网络里程碑 |

保留字节统计覆盖 vector/string 的 capacity；节点和对象开销另用数量约束。这不是整个进程的精确堆/RSS 上限。回放序列化、容器扩容以及外部快照回调仍可能产生有界临时副本；回调自行分配的数据不能由接收方在其创建之前限制。

回放使用明确的小端整数/浮点位序，保持现有 x86 文件布局。修复了录制过程中保存时元数据未更新、重新开始后旧统计残留的问题。TCP 客户端退出保存条件已允许保存达到容量后停止的录制前缀；真实长时间录制的文件持久化还需后续验收。

UDP 的 RTT 输入和求和有界，重传 ACK 不参与不明确的 RTT 采样；重传间隔使用毫秒绝对偏差，修正了原来的平方毫秒量纲。统计读写受同一互斥锁保护，回调在锁外执行。完整拥塞控制、去重、乱序、序号回绕仍需网络故障矩阵验证。

## 验证证据

- [局部预验收原始结果](../optimization/benchmarks/memory-core-preflight-20260909/report.json)：72 个 C++ 测试，全部执行，无失败/禁用；启用 ASan 与 UBSan。包括 1000 次快照保存、100 次真实 UDP 填满/ACK 清空循环、并发发送、超长/损坏载荷、发送失败、重传耗尽和恢复。
- 回放满载用例记录 100000 个合成输入帧，每帧 22 槽位；这项测试验证容量与编解码，不是真实完整比赛性能证明。
- [真实引擎 Release 结果](../optimization/benchmarks/memory-core-preflight-20260909/engine-memory-native.log)和 [ASan/UBSan 结果](../optimization/benchmarks/memory-core-preflight-20260909/engine-memory-sanitized.log)：各 1498 项断言、128 个权威确认帧、64 次产生回滚的 Tick；逐确认帧核对哈希，每批核对完整状态摘要，再通过真实 GameEnv 重播录制。两个场景的最大初始快照为 91416 字节，观察到的历史峰值为 438176 字节。覆盖 4 和 22 个受控槽位，双方阵容都是 11v11。超大容量回调用例是故障注入，不冒充自然快照增长。
- [Release 实际客户端故障探测](../optimization/benchmarks/udp-capacity-release-20260909-final/report.json)与 [检测构建故障探测](../optimization/benchmarks/udp-capacity-sanitized-20260909-final/report.json)：非法槽位、无 ACK、非法权威槽位、接收缓冲满载四个场景。普通故障退出码 1 必须同时有正确原因，检测器输出不能算预期退出。
- [Release 实际服务器/客户端联调](../optimization/benchmarks/udp-native-pair-release-20260909-final/report.json)与 [检测构建联调](../optimization/benchmarks/udp-native-pair-sanitized-20260909-final/report.json)：先转发 11 个权威帧和帧 0、10 的哈希报文，客户端未报告状态不一致；随后停止回包，客户端报告重传耗尽并退出。本探测记录报文和进程结果，没有单独断言客户端的最终确认计数。服务器由探测器结束进程，此用例不证明服务器析构/退出时无泄漏。
- 本轮实际编译 native 的 `football_server`、`football_client`、`football_client_tcp`、`engine_memory_contract`，以及独立 Asio 的两个 UDP 目标。检查了完整检测构建配置中 130 条编译命令的 ASan/UBSan 标志；该数字不是本轮重编译单元数。
- Release 引擎 SHA256 仍为 `15336a4efd865434190fbd63914ad0286aaf43bebd9043c6b2892b306d256dcb`，没有替换原始性能基线或优化后归档。正式前置门禁仍需在本任务实施完成后按源码指纹重验。

## 修复过程中发现的问题

1. 旧测试中的方向值超过协议范围，改用合法且可区分的输入保留原断言意图。UBSan 检出测试把十字节打包输入中的浮点成员按引用传给 GoogleTest；改为先按值读取，没有关闭检测器。
2. 原计划用 4096 字节 UDP 报文对应接收缓冲大小，真实本地路径探测显示 1472 字节可达、2048 字节及以上丢失，故将单报文预算设为 1200 字节。更大状态需另行实现分片。
3. 22 槽位客户端输入需要 271 字节应用载荷，原 256 字节发送缓冲装不下；改为按最大合法槽位分配栈缓冲。心跳按完整消息消费，避免把其载荷字节误认成消息类型。旧独立服务器不再发送客户端没有协商支持的 Delta 格式。
4. 联调探测最初把已关闭的占位套接字残留记录当成服务器已监听；修正为核对服务器进程实际持有的 socket inode。[失败记录](../optimization/benchmarks/udp-native-pair-sanitized-20260909-b/pair_packets.json)保留。
5. 修正探测器后，检测构建复现了真正的启动缺陷：[原报文记录](../optimization/benchmarks/udp-native-pair-sanitized-20260909-c/pair_packets.json)显示客户端发 Ready 后还在加载 GameEnv，服务器提前开赛并重传超时。Ready 现移到引擎初始化之后；未就绪连接不发送游戏心跳，有独立 30 秒加载期限；就绪后的原心跳期限不变。修复后的两类构建均通过实际联调。
