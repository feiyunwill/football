# 硬件渲染窗口手感诊断与动画重选实验

归属 `ms-22.1 → plan-22.1.2 → task-22.1.2.2`。此报告记录诊断进展，不构成正式验收；`feel_regression` 仍未就绪。

软件渲染下观察到的输入步进延迟不能代表硬件渲染产品窗口。因此扩展 `feel_latency_window.py`，在实际 `standalone_game` 窗口中加载私有 D3D12 Mesa 驱动，以 XTEST 发送方向键，并核对产品进程确实映射该驱动。短场次聚合工具 `feel_latency_cohort.py` 使用固定种子、每场 4 次按键，过滤开球和定位球状态，保留未响应按键。按键方向优先选为当前受控球员水平运动的反方向，以检验方向反转时的手感。跟踪库记录每步的 `game_mode` 和球员方向速度。这里的“响应”指相同受控球员在按键方向上的速度变化达到 0.1；画面交换只说明提交了新帧，尚未证明具体球员动作出现在像素中。

| 实验 | 按键 / 进入步进 / 检测到响应 | 进入步进 p95 | 已响应样本的速度变化 p95 | 已响应样本的随后交换 p95 |
| --- | ---: | ---: | ---: | ---: |
| 基线 | 60 / 60 / 34 | 36.825 ms | 282.072 ms | 285.170 ms |
| 受控球员移动动画重选候选 | 60 / 60 / 36 | 33.313 ms | 78.167 ms | 84.762 ms |

候选改动使外部控制的移动动画每 20 ms 有重选机会，缩短连续移动重选的延迟，并允许在持球或远离球时重选。15 个相同种子的短场次中，已响应样本的 p95 明显下降；但 60 次按键仍有 **24 次未在 340 ms 按住窗口内达到响应阈值**，已响应子集的 p95 也超过 50 ms。未响应中有 23 次按键方向与原运动方向相反，22 次在按键期间测得的有符号速度变化为负。不能用已响应子集的 p95 代表全部动作，也不能把本候选标为产品级达标。

正式质量编排 `python3 .project/quality.py run task-22.1.1.1` 还发现候选改变了固定比赛的战术架构结果：`engine_ai_tactical_state_contract` 的 960 帧与 27,618 项断言通过，但定位球计数为 326，原契约要求 331；因此 `architecture_regression` 失败。候选**已从运行时代码撤回**，补丁仅保存在证据包中供后续分析。失败原始日志为 [`architecture_regression-1790794114300310152.log`](../optimization/evidence/architecture_regression-1790794114300310152.log)，SHA-256 `89bf468f5bcf69a8837bdd48a39e97cde326b3c12b4bbceeb8f2e11ceaf55d33`。下一步需定位手动方向与自动移动修正、动画选择之间的冲突，再设计不改变既有比赛契约的方案，并以完整响应率和正式门禁复核。
