## 具体实现

- `server_state.py` 维护严格参数、完整消息解码、输入窗口和发送队列。异常返回固定原因；未知消息不跳过，FrameInput 数量在等待正文前检查。方向、按钮、槽归属、重复冲突和帧范围全部验证成功后才入队。
- `server_runtime.py` 是实际网络与引擎唯一所有者，使用一个事件循环、一个监听任务、一个维护任务及每连接一收一发任务。连接关闭期间仍占用连接名额，过载不会增加额外工作线程。
- `server_api.py` 提供原有同步与异步导入入口。同步 API 向一个自有线程提交最多 8 个待处理命令；关闭请求独立且合并。异步 `start()` 的引擎初始化与后续监听必须在同一线程，检查在线程/循环/套接字所有权改变前完成。
- 输入窗口保留提前收到的当前帧和未来输入，收集开始不再清空。相同重复幂等，冲突重复拒绝；满队列不覆盖已有数据。断线保留已接受的当前帧，清除该槽未来帧，bot 仅填充缺少的当前输入。
- 同步默认协商握手、异步默认 server-first 握手都保留。比赛开始后，server-first 入口也等待 ReconnectRequest；新普通会话不能跳过当前状态初始化直接入场。
- 会话令牌使用非零随机 64 位值；重复生成尝试也有上限。恢复必须属于已离线会话，发送下一帧编号对应的快照，等待 Ready 时 bot 继续工作，后续权威帧在同一发送预算内排队，Ready 后按顺序释放再交还控制。令牌错误或容量耗尽不会抢占其他 bot。
- 入站消息有速率、完整消息、握手、Ready、空闲截止。发送截止从初次入队计算，包括延迟发送历史，活动写入仍计量。窗口、发送和会话计数均在关闭时释放。

## 实际复现的生命周期缺陷

第一轮 106 项断言全部通过，但 stderr 出现 Windows `Cancelling an overlapped future failed`，所以 runner 判整体失败。原因是取消重叠 I/O 之前关闭了套接字。现在先 shutdown/取消读写，任务结束后再关闭描述符；即使读任务尚未开始，完成回调也会收回套接字。

实际异步客户端联调也复现了相同句柄问题。客户端现在区分 OS connect 任务和外层握手任务，以每连接一份完成 Future 等待取消，避免循环等待或未观察异常。服务端清理由单独任务持有，取消某个等待者不会中断资源回收；重复 stop 不会在事件循环退出时创建遗漏的清理任务。

新增停止语义回归先复现：`stop(); await run_one_frame()` 在清理获得执行机会前仍能推进引擎。现在 stop 同步设置停止状态，并唤醒收集者；停止后的初始化、监听和推进均拒绝，关闭本身可反复等待。

另一个新增回归先复现：先在 A 线程初始化引擎，再在 B 线程监听，会迁移运行时循环并导致 A 无法关闭。现在保留初始化线程对象作为所有权标识，拒绝跨线程迁移，原所有者仍可继续正常启动、推进和关闭。

服务端空闲截止联调发现 Python 客户端没有周期性主动心跳。现在同步接收循环和异步 watchdog 按有界队列周期发送，等待大厅时不依赖游戏输入。采用主动周期发送，避免与原生 TCP 服务端的心跳回显形成无限互相回显。

## 容量与证据范围

| 对象 | 默认上界 |
| --- | --- |
| 连接/控制槽 | 32 连接、22 槽；关闭中的连接计数不提前减去 |
| 输入 | 128 帧、拥有的输入值 256 KiB |
| 接收 | 每连接 8 KiB bytearray 容量 |
| 发送 | 每连接 256 条、2 MiB，含活动写入与等待 Ready 的历史 |
| 恢复快照 | 1 MiB |
| 完整入站消息 | 1,000 条/秒，突发 128 |
| 控制请求 | 同步入口最多 8 个待处理 API 命令，加一个合并的关闭请求 |

统计计量自有保留数据；字典、任务等控制对象由条数另行限制。操作系统缓冲、临时编码/副本、调用者持有的对象、原生/RSS/GPU 内存不在这些字节计数中。原生引擎调用不能被 Python 任务取消强制中断。

真实 TCP 检查包括 22 客户端各提交 32 帧、704 项未来输入和权威帧消费；慢读端触发实际写超时后其他连接仍可使用；40 次连接关闭无会话墓碑；违规输入不进入引擎；恢复前快照、两帧延迟历史和交还顺序准确；大厅等待超过三个空闲周期不断线；控制线程阻塞期间第九项并发命令被容量拒绝。引擎适配器仅归约实际 SlotInput 字节，绝不替代 GameEnv 确定性证据。
