# 容量与回放验收适配当前产品协议

归属 ms-21.1 → plan-21.1.2 → task-21.1.2.1。原内存预算检查在 GoogleTest v1.14.0 本地源码缓存缺失处停止；补齐指定版本后，它又调用发送旧 9 字节 TCP 会话开始和裸 UDP `Connect` 的探针。当前 `football_client_tcp` 与 UDP 产品入口使用版本化产品会话、UDP 返回路径挑战及带连接 ID 的可靠封包。旧探针的“连接失败”发生在初始化之前，不能证明容量逻辑失败或通过。

验收脚本现使用当前协议的真实 TCP/UDP 双玩家探针：两种传输均完成 50 帧权威流，两份输入和五个服务端哈希一致。队列、输入、历史和发送缓冲的边界仍由普通与 sanitizer 构建下的原生单位契约检查。UDP 探针增加了 64 字节返回路径握手及连接 ID 封包；TCP 探针运行真实产品客户端。回放目录探针也改为真实产品服务端和双客户端，检查文件数、总字节配额、拒绝时旧文件不变、容量释放后恢复，以及仅清理由本程序拥有的临时文件。

回放独立解码器识别当前 `FNRPLY1` 的 40 字节产品封套，仍兼容旧版原始格式以测试最大 100,000 帧文件。固定回放代理只转发实际服务端至第 20 帧哈希的字节，避免 sanitizer 下异步退出前多确认一帧；两个客户端均保存 21 帧、3 个哈希，保存的每帧输入与代理捕获的权威包逐项相同。完整回放持久化独立检查通过 224 项执行、零跳过；内存预算独立检查通过 1,399 项执行、零跳过。压缩报告见 [`memory_budget_product_protocol_20260928.json.gz`](../optimization/evidence/memory_budget_product_protocol_20260928.json.gz) 与 [`replay_product_persistence_20260928.json.gz`](../optimization/evidence/replay_product_persistence_20260928.json.gz)。

容量检查复用框架验收建立的固定 Python 依赖环境，避免系统 Python 缺少 `pytest` 导致测试未执行。当前 TCP 产品探针检查错误 Ready 后席位替换；UDP 产品探针检查正常返回路径握手、双人权威流及可靠封包，**尚未证明 UDP 错误 Ready 后立即替换席位**。此边界留给 ms-23.1 网络可靠性验收，不能由本轮正常会话通过推断为已解决。最终源码上的 `python3 .project/quality.py run ms-21.1` 已完成，所有依赖检查以及内存、回放和性能门禁均通过，`ms-21.1` 状态为 `verified`。
