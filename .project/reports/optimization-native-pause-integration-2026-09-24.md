# 原生暂停恢复：接入顺序与验收要求

归属 ms-23.1 → plan-23.1.1 → task-23.1.1.2，并与 ms-22.1 输入隔离、ms-25.1 接管行为共同验收。状态为接入设计，未宣称实现完成。当前 28/7449 控制协议及 30/7020 输入周期候选通过只是组件证据。

现有原生 Run 在唯一帧线程计算初始 hash、提交恢复 Ready、消费输入并执行 GameEnv；应保留这一所有权。网络 I/O 回调负责有限的字节解析和请求入队，不能计算引擎状态或在帧中途提交暂停。原生 LoadHello 当前仅包含旧的 18 字节描述或附带多席位标记的 22 字节负载，不能因引入 kind19/20/21 的常量便认为完成了控制能力协商。

现有 Python 实现提供可核对的行为参考：暂停和准备恢复各推进 epoch，准备恢复的 Running 提交保持同一个 epoch 和边界；改变 epoch 时清空未来输入；所有 Streaming peer 的控制 ACK 满足前才推进屏障，ACK 超时采用 min(3秒, ready_timeout)。重复 ACK 不能满足更晚屏障，旧输入即使丢弃也验证数值与所有权；未来 epoch、暂停时输入和绕过 epoch 的旧格式输入被拒绝。结束流程采用自己的有界退出路径。

下一实施阶段按以下顺序完成实际路径，不能只增加一个未被产品调用的状态机：

1. 明确并测试控制能力协商，以及握手、快照和 Ready 的 epoch/phase/boundary 语义；兼容现有多席位报文的规则必须显式定义。错误能力、过期 Ready、恢复期间 epoch 改变都要有反例。
2. 将已验证的控制与周期输入实现接入实际原生服务帧线程。在帧边界采集 hash、停止推进、清空旧未来输入；心跳、断线清理、快照发送和有界 ACK 超时仍需继续。恢复前完成准备/ACK/提交，重置绝对帧时限，不能补跑暂停期间的墙钟帧。
3. 接入真实客户端：接收控制时按权威边界处理；由 GameEnv 所属线程校验 frame/hash 后 ACK。清空旧输入缓存、隔离暂停期间按键及恢复时仍按住的设备输入；渲染与窗口事件持续处理。重新连接必须恢复控制状态，不能用旧 epoch 的输入或 Ready 重新获得控制。
4. 给 Host 所有者提供控制入口，并由真实 Host/Join 菜单使用。不能把客户端本地 K 键输入隔离当作整局暂停，也不能让普通 Join 客户端取得主机权限。保存/恢复检查点、场景和回放路径仍按原菜单功能逐项补齐。
5. 在实际 Release/full Debug TCP/UDP 产品上验证两个客户端、双方席位、暂停期间断线、ACK 延迟/重复/丢失、旧 epoch 输入、连续快速切换、关闭/结束，以及真实窗口设备输入。检查帧与 hash 在暂停时稳定，恢复后权威和独立回放一致，且没有输入边沿重复。最终运行完整相关门禁。
